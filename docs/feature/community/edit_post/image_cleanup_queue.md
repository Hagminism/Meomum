# 게시글 수정 이미지 정리 큐

## 1. 한 줄 요약

게시글 수정 과정에서 DB 변경은 성공했지만 Storage 이미지 삭제가 실패할 수 있습니다. 이때 삭제하지 못한 이미지 경로를 `community_image_cleanup_queue`에 남겨 두고, 다음 앱 실행·커뮤니티 화면 진입·앱 재개 시 다시 삭제하는 구조입니다.

이 큐는 삭제 작업이 끝날 때까지 사용하는 작업 큐입니다. 영구적으로 모든 시도를 보존하는 감사 로그 테이블은 아닙니다.

## 2. 왜 큐가 필요한가

게시글 수정에는 서로 다른 두 저장 공간이 관여합니다.

| 대상 | 저장 내용 | 트랜잭션 처리 |
| --- | --- | --- |
| PostgreSQL | 게시글 본문, 게시글 이미지 메타데이터 | `update_post_with_images` RPC에서 원자적으로 처리 |
| Supabase Storage | 실제 이미지 파일 | PostgreSQL 트랜잭션에 포함되지 않음 |

예를 들어 사용자가 기존 이미지 A를 삭제하면 다음 두 작업이 필요합니다.

1. `post_images`에서 이미지 A의 메타데이터를 제거합니다.
2. Storage에서 실제 이미지 A 파일을 제거합니다.

1번과 2번을 하나의 트랜잭션으로 묶을 수 없기 때문에, Storage 삭제가 실패하면 DB에는 더 이상 사용하지 않는 파일이 남을 수 있습니다. 큐는 이 작업을 나중에 다시 수행할 수 있도록 연결해 주는 보상 처리 장치입니다.

## 3. 게시글 수정 전체 흐름

게시글 수정 시 애플리케이션은 다음 순서로 동작합니다.

```text
신규 이미지 Storage 업로드
        ↓
최종 이미지 목록 구성
        ↓
update_post_with_images RPC 호출
        ↓
게시글·post_images·삭제 대상 큐를 DB 트랜잭션으로 반영
        ↓
DB 수정 성공
        ↓
삭제 대상 기존 이미지의 Storage 파일 삭제
        ↓
성공하면 큐 항목 삭제 / 실패하면 재시도 정보 기록
```

### 3.1 신규 이미지 업로드

수정 화면에서 새 이미지를 추가하면 먼저 Storage에 업로드합니다. 업로드가 끝난 이미지의 `storage_path`와 `public_url`을 저장해 두었다가 게시글 수정 RPC에 전달합니다.

이 단계에서 일부 파일만 업로드된 뒤 다음 파일 업로드가 실패할 수 있습니다. 이미 업로드된 파일은 게시글에서 참조되지 않으므로 먼저 삭제를 시도하고, 삭제까지 실패한 경로만 큐에 등록합니다.

### 3.2 DB 수정 RPC

`update_post_with_images` RPC는 현재 로그인한 사용자가 작성한 게시글인지 확인한 후 다음 작업을 하나의 DB 트랜잭션으로 처리합니다.

- 게시글 본문과 위치 정보 수정
- 기존 `post_images` 전체 교체
- 기존 목록에는 있었지만 최종 이미지 목록에는 없는 Storage 경로 계산
- 삭제 대상 Storage 경로를 큐에 등록
- 수정 결과와 삭제 대상 경로 반환

삭제 대상 큐 등록이 실패하거나 게시글 수정 중 다른 오류가 발생하면 DB 트랜잭션 전체가 취소됩니다. 따라서 기존 게시글 메타데이터만 삭제되고 큐 기록이 빠지는 상태를 방지합니다.

### 3.3 DB 수정 이후 Storage 정리

DB 수정이 성공한 뒤에야 삭제 대상 기존 이미지의 실제 Storage 파일을 삭제합니다.

- Storage 삭제 성공: 큐 항목을 삭제합니다.
- Storage 삭제 실패: 큐 항목을 유지하고 실패 횟수·오류·다음 재시도 시각을 기록합니다.

Storage 정리가 실패해도 게시글 DB 수정 자체는 성공한 상태이므로 사용자는 수정 완료 결과를 받습니다. 남은 파일 정리는 큐를 통해 나중에 재시도합니다.

## 4. 큐 테이블의 의미

테이블에는 `completed` 같은 완료 여부 컬럼이 없습니다. 큐 항목의 존재 여부로 상태를 표현합니다.

| 상태 | 테이블 상태 | 의미 |
| --- | --- | --- |
| 재시도 대기 | 행이 존재하고 `next_retry_at <= 현재 시각` | 지금 정리를 시도할 수 있음 |
| 재시도 예약 | 행이 존재하고 `next_retry_at > 현재 시각` | 이전 삭제 실패로 다음 시각까지 대기 중 |
| 정리 완료 | 행이 삭제됨 | Storage 삭제와 큐 완료 처리가 끝남 |

주요 컬럼은 다음과 같습니다.

| 컬럼 | 설명 |
| --- | --- |
| `account_id` | 큐 항목을 만든 사용자 계정 |
| `storage_path` | 삭제해야 하는 Storage 파일 경로 |
| `attempt_count` | 삭제 실패 누적 횟수 |
| `last_error` | 가장 최근 삭제 실패 메시지 |
| `next_retry_at` | 다음 삭제를 시도할 수 있는 시각 |
| `created_at` | 큐 항목이 처음 생성된 시각 |

`(account_id, storage_path)`에 unique 제약이 있어 같은 사용자의 같은 경로가 중복 등록되지 않습니다.

## 5. 대표적인 두 가지 실패 흐름

### 5.1 기존 이미지 삭제 실패

사용자가 기존 이미지 A를 제거하고 새 이미지 C를 추가했다고 가정합니다.

```text
기존 이미지: A, B
최종 이미지: B, C
삭제 대상: A
```

1. C를 Storage에 업로드합니다.
2. RPC가 `post_images`를 B, C로 갱신합니다.
3. RPC가 A의 Storage 경로를 큐에 기록합니다.
4. 앱이 A의 Storage 삭제를 시도합니다.
5. 삭제 성공 시 A의 큐 행을 삭제합니다.
6. 삭제 실패 시 A의 큐 행에 실패 정보와 다음 재시도 시각을 기록합니다.

DB 수정은 이미 성공했기 때문에 화면에는 B, C가 정상적으로 표시됩니다. A는 큐의 재시도 대상으로만 남습니다.

### 5.2 신규 이미지 정리 실패

새 이미지 C를 Storage에 업로드했지만 게시글 수정 RPC가 실패한 경우입니다.

1. C는 아직 게시글에서 참조되지 않습니다.
2. 앱이 C의 Storage 삭제를 즉시 시도합니다.
3. 삭제 성공 시 별도 큐가 필요하지 않습니다.
4. 삭제 실패 시 C의 경로를 큐에 등록합니다.

이 경우에는 게시글 수정이 실패하므로 사용자에게 오류를 전달합니다. 동시에 C를 나중에 정리할 수 있도록 큐에 남깁니다.

## 6. 재시도 정책

실패가 기록될 때 DB RPC가 `attempt_count`를 증가시키고 `next_retry_at`을 계산합니다.

| 실패 전 `attempt_count` | 다음 재시도 간격 |
| ---: | ---: |
| 0 | 1분 후 |
| 1 | 10분 후 |
| 2 | 1시간 후 |
| 3 이상 | 24시간 후 |

최대 시도 횟수로 영구 중단하지 않고, 계속 실패하면 24시간 간격으로 재시도합니다.

## 7. 재시도가 실행되는 시점

앱에 별도 백그라운드 타이머를 계속 실행하지 않습니다. 다음 이벤트가 발생할 때 만료된 큐 항목을 확인합니다.

- 앱이 처음 실행될 때
- 커뮤니티 화면에 진입할 때
- 앱이 백그라운드에서 다시 활성화될 때

한 번 조회할 때 최대 20개만 가져오며 `next_retry_at`이 빠른 항목부터 처리합니다. 또한 다음 보호 장치가 있습니다.

- 이미 실행 중이면 동시에 다시 실행하지 않음
- 일반 재시도는 마지막 실행 후 30초 이내면 생략
- Storage 삭제 성공 후에만 큐 행을 삭제
- 삭제 실패 시 큐 행을 유지하고 다음 시각을 갱신

따라서 큐 항목이 많아져도 앱 실행마다 전체 큐를 한 번에 처리하지 않습니다.

## 8. 보안 처리

큐에는 사용자 소유 이미지 경로만 들어가야 합니다.

- Storage 경로는 `accounts/{현재 계정 ID}/...` 형식이어야 합니다.
- 큐 등록 RPC가 현재 계정의 경로인지 검증합니다.
- 수정 RPC도 전달된 모든 이미지 경로의 계정 소유 여부를 검증합니다.
- 큐 조회와 삭제는 현재 계정의 행만 대상으로 합니다.
- 테이블 직접 입력 대신 보안 정의 RPC를 통해 큐를 등록합니다.

이를 통해 다른 사용자의 이미지 경로를 큐에 등록하거나 삭제 대상으로 삼는 것을 방지합니다.

## 9. 큐는 로그 테이블인가?

정확히는 로그 테이블보다는 운영용 작업 큐입니다.

| 구분 | 작업 큐 | 감사 로그 |
| --- | --- | --- |
| 목적 | 아직 끝나지 않은 작업을 재시도 | 과거 이벤트를 영구 보관 |
| 성공 시 | 행 삭제 | 기록 유지 |
| 실패 시 | 다음 실행 시각과 오류 갱신 | 새 로그 행 추가 |
| 현재 테이블 | 해당함 | 해당하지 않음 |

`attempt_count`, `last_error`, `created_at`을 통해 현재 정리 상태를 확인할 수는 있지만, 성공한 정리의 이력까지 보관하지는 않습니다. 영구적인 감사 이력이 필요해지면 이 큐와 별도의 로그 테이블을 추가해야 합니다.
